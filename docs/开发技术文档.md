## 1. 工程速览

| 项 | 值 |
| --- | --- |
| 形态 | Flutter 宿主 App（Android），内嵌 WebView 承载「小程序」 |
| 包名 | `com.lemonlite.lemonlite` |
| 版本 | `0.6.0+6`（`pubspec.yaml`） |
| 框架版本常量 | `kFrameworkVersion = '0.1.5'`（`lib/core/globals.dart`） |
| Dart 代码 | 52 个文件 / 约 18,600 行（`lib/`） |
| 测试 | 8 个文件 / 190 余个用例（`test/`） + 59 个服务端用例（`server/test/`） |

| minSdk | 24（`dynamic_color 1.9` 要求） |

**一句话定位**：这不是「用 Flutter 渲染小程序」，而是「用 Flutter 做宿主外壳 +
WebView 做逻辑层 + 一条 JSBridge 把两边接起来」。所以你会看到大量
「宿主提供能力 → 网页调用 → 宿主回包」的代码，而几乎没有 Flutter 侧的
动态 UI 渲染。

## 2. 分层架构

### 依赖方向

```
        ┌──────────────────────────────────────────┐
        │  pages/  （Widget、路由、Overlay）        │
        └───────────────┬──────────────────────────┘
                        │
        ┌───────────────▼──────────────────────────┐
        │  bridge/ （JSBridge 实现、注入脚本）      │
        └───────────────┬──────────────────────────┘
                        │
        ┌───────────────▼──────────────────────────┐
        │  data/ （models / repositories / services）│
        └───────────────┬──────────────────────────┘
                        │
        ┌───────────────▼──────────────────────────┐
        │  core/ + theme/ （宿主级、无业务上下文）   │
        └──────────────────────────────────────────┘
```

**规则**：下层不认识上层。`core/` 与 `theme/` 绝不 import `pages/`、`bridge/`
或 `data/`；`data/` 只依赖 `core/` 与 `theme/`。

唯一的反向依赖是 `settings_service.dart` → `theme/app_theme.dart`：
它需要 `AppTheme` 里的默认种子色常量。这是刻意保留的（把默认值放在主题层，
设置层只负责持久化），不要为了「纯洁」把它复制一份到 data 层。

**唯一的例外**是 `pages/miniapp/miniapp_host.dart` 与 `miniapp_page.dart` 互相 import ——
它们是同一个功能的「管理层」与「视图层」（菜单里的关闭/后台运行需要 host，
host 需要创建会话视图）。文件头注释里写明了这个取舍：
把视图工厂外置只会让调用方更啰嗦。

### 三个全局单例

`main.dart` 里按顺序初始化，**顺序不能反**：

```dart
final SettingsService settings = await SettingsService.init();
PermissionService.init();      // 同步单例，桥接层每次调用都要查
ApplicationRegistry.init();    // 应用清单，页面都从它取
await AppInfo.load();          // 版本号，设置页要同步显示
```

前两个是**同步单例**（`init()` 不返回 Future）：因为它们要在 Widget 树建立之前就绪，
而桥接层的调用可能发生在任何时刻。`SettingsService` 必须 `await` 是因为
`SharedPreferences.getInstance()` 本身是异步的。

**为什么用单例而不是 Provider 注入**：`MarketRepository`、`BridgeApi`
都不是 Widget，通过 Provider 拿会多一层 `BuildContext` 依赖，
而桥接层的回调经常拿不到 context（见 `core/globals.dart` 里的 GlobalKey 说明）。

## 3. 主题链路

这是全工程最完整的一条链，改动任何一环都要走完整条：

```
SettingsService（持久化：theme_mode / seed_color / use_dynamic_color）
    → ThemeController（合成最终 ColorScheme）
    → DynamicColorBuilder（Android 12+ 注入壁纸色）
    → MaterialApp.theme / darkTheme（宿主 UI 生效）
    → ThemeInjector（同一份配色 → --md-* CSS 变量）
    → 注入到 WebView（window.__LEMONLITE_THEME__ + JS SDK）
    → 小程序页面 <html> 上的 CSS 变量
```

### 为什么只有一份配色来源

如果宿主和 WebView 各算一次，就会出现「宿主是紫色、小程序还是蓝色」的错位。
所以 `ThemeInjector` 的输入**只能**是 `ThemeController` 产出的那个 `ColorScheme`，
不存在第二处 `fromSeed` 调用。

### 注入时序（防闪烁）

`miniapp_page.dart` 的 `_buildUserScripts()` 按固定顺序生成 `UserScript`：

```
1. 主题数据（window.__LEMONLITE_THEME__ = {...}）   ← AT_DOCUMENT_START
2. JS SDK（LemonJsSdk.source）                      ← AT_DOCUMENT_START
3. 模块/扩展注册表（window.__LEMONLITE_BUNDLES__）  ← AT_DOCUMENT_START
4. 模块/扩展的 CSS / JS                             ← 按 manifest 的 runAt
```

**为什么数据在前、SDK 在后**：SDK 初始化代码的最后一行会读
`window.__LEMONLITE_THEME__` 并立刻把 `--md-*` 写进 `<html>`。
这个动作发生在 `<body>` 渲染之前，所以不会出现「先白底再变深色」的闪烁。
反过来的顺序做不到这件事（数据还没到）。

**为什么扩展排在 SDK 之后**：扩展脚本要能一上来就用 `window.lemonlite.*`。

### 热更新

用户在设置页切主题时，WebView 不会重建（重建会丢小程序状态）。
走的是 `evaluateJavascript` 调 SDK 的 `__applyTheme(payload)`：

```dart
controller.evaluateJavascript(
  source: ThemeInjector.buildLiveUpdateScript(payload),
);
```

`_syncTheme()` 里有一个 `json == _appliedThemeJson` 的短路，
避免同一份主题反复下发。页面 `onLoadStop` 时会 `force: true` 再下发一次 ——
因为 `UserScript` 里的快照可能已经过期（用户在小程序加载期间切了主题）。

### CSS 变量命名

`--md-<kebab-case(ColorScheme 字段名)>`，共 **36 个颜色变量**（含 3 个别名，见下表）。

亮度不占 CSS 变量，而是写成 `<html>` 上的两个属性（JS SDK 的 `applyTheme` 负责）：

```html
<html data-md-brightness="dark" style="color-scheme: dark">
```

页面里要按亮度分支，用 `[data-md-brightness="dark"] { … }`，不要自己猜。

```
primary           → --md-primary
primaryContainer  → --md-primary-container
onSurfaceVariant  → --md-on-surface-variant
```

**三个兼容性别名**（不要删，老小程序在用）：

| 变量 | 实际映射 | 原因 |
| --- | --- | --- |
| `--md-background` | `surface` | M3 已把 background 并入 surface，但老页面写的是它 |
| `--md-on-background` | `onSurface` | 同上 |
| `--md-surface-variant` | `surfaceContainerHighest` | 语义等价，且能避开 Flutter 的弃用告警 |

### 硬编码色值的唯二例外

1. 二维码画布（扫描器要求纯黑白）；
2. 色块/方块上的文字（按对比度选黑或白）。

除此之外**一律**走 `Theme.of(context).colorScheme`。这条规矩有实际收益：
换主题时不需要逐个页面检查。

## 4. JSBridge 协议

### 三层分工

```
injected_js.dart    JS 侧：把 callHandler 包成 Promise，做参数校验
      ↕  callHandler('lemonlite', { method, params })
js_bridge.dart      Dart 侧：注册 handler、解析、统一包错误
      ↕  dispatch(method, params)
bridge_api.dart     Dart 侧：每个 API 的实际实现
```

`js_bridge.dart` 刻意保持很薄（约 120 行）：它只做三件事 —— 注册、解析、包错误。
任何「业务逻辑」都不该出现在这里。

### 报文格式

**JS → Dart**

```js
window.flutter_inappwebview.callHandler('lemonlite', { method: 'setTitle', params: { title: 'x' } })
```

**Dart → JS（成功）**

```json
{ "code": 0, "data": { ... } }
```

**Dart → JS（失败）**

```json
{ "code": 10001, "message": "title 不能为空" }
```

`code === 0` 是唯一的成功判据。JS 侧 `invoke()` 看到非 0 就 `reject`。

### 错误码表

| code | 含义 | 抛出位置 |
| --- | --- | --- |
| `0` | 成功 | — |
| `10001` | 参数错误 | `BridgeApi` 各方法 / JS 侧前置校验 |
| `10002` | 桥接未就绪（页面不是容器打开的） | `injected_js.dart` 的 `waitForBridge` 超时 |
| `10003` | 不支持的能力（未知 method、不支持的协议） | `dispatch` 的 `default` 分支 |
| `20001` | 网络错误 | `request()` |
| `20002` | 请求超时 | `request()` |
| `20003` | HTTP 状态错误 | `request()` |
| `30001` | 存储读写失败 | `setStorage` / `getStorage` |
| `40001` | **保留值，0.3 起不再抛出** | 见下方说明 |
| `90001` | 兜底内部错误 | `js_bridge.dart` 的 `catch` |

**关于 40001**：0.2 用它表示「权限被拒绝」。0.3 把权限收窄成浏览器受控资源后，
拒绝发生在 Chromium 层（网页拿到 `NotAllowedError` DOMException），
根本走不到 JSBridge。常量保留是为了不改变已发布版本里
`if (err.code === 40001)` 这类判断的含义（删掉会变成 `undefined === 40001`，
静默失效）。它现在标了 `@Deprecated`。

### 一致性约束（有测试守着）

`test/permission_test.dart` 里有一条断言：JS SDK 里每个 `invoke('x')`
必须在 `bridge_api.dart` 的 `dispatch` 里有一个 `case 'x':`，反之亦然
（模块 action 的 case 会被排除）。

**这意味着加 API 必须同时改两个文件**，否则 `flutter test` 直接红。
这是刻意的：单边改动会在运行时变成「JS 报 10003」或「Dart 代码永远不执行」，
两者都很难通过读代码发现。

### 响应式外壳：手机底部栏 / 平板侧边栏

按屏幕**最短边 dp** 判定（`kTabletMinShortestSide = 600`，取自 Material 3
的 window size class）：

```dart
bool useWideLayout(BuildContext context) {
  final Size size = MediaQuery.sizeOf(context);
  return size.shortestSide >= kTabletMinShortestSide;
}
```

**为什么用最短边而不是宽度**：横屏手机宽度可以到 900dp 以上，
但最短边仍是 400 左右 —— 那种尺寸上放侧边栏会把内容区挤得很窄。
`test/account_test.dart` 里有一条断言专门钉住「Pixel 7 横屏仍判为手机」。

**为什么不用 dpi**：dpi 只说明像素密度，400+ dpi 的旗舰手机一大堆，
按 dpi 判会把它们全判成平板。最短边（逻辑像素）才对应「能放多少内容」。

平板布局用 `NavigationRail`（左侧）+ `VerticalDivider` + `Expanded`；
手机用 `NavigationBar`（底部）。两者共用同一份 `NavigationDestination` 语义。

## 5. 小程序会话与后台运行

### 为什么小程序不是路由

「后台运行」要求退出页面后**页面状态还在**（WebView 不重载、JS 不重启）。
而路由一旦 `pop` 就会 `dispose`，WebView 随之销毁。

所以小程序是**叠在 AppShell 的 Stack 里的一个层**：

```
AppShell
└── Stack
    ├── 第一层：Scaffold（导航 + 当前 Tab）      ← 普通 widget
    └── 第二层：MiniappHost.buildLayer()          ← 盖住导航
        └── IndexedStack
            ├── 会话 A 的 MiniappSessionView（WebView）
            └── 会话 B 的 MiniappSessionView（WebView）

（从任意页面 push 出来的路由 / 对话框在 MaterialApp 的 Navigator 里，
  它们天然压在 AppShell 之上 —— 所以「小程序里点菜单打开权限管理」能看见。）
```

**⚠️ 曾经用的是 `OverlayEntry`，那是个真 bug，别再改回去**

0.3 及之前把会话层插进 Navigator 的 Overlay。看起来更「高层」，
但 Navigator 每次路由变化都会执行：

```dart
// navigator.dart, _flushHistoryUpdates
overlay?.rearrange(_allRouteOverlayEntries);
```

而我们的 entry **不在**那个列表里，于是 `Overlay.rearrange` 把它当作
「多余条目」放进 `old` 残余集合，然后
`insertAll(_entries.length, old)` 把它挪到**最顶层**。

症状：点小程序菜单 → 权限管理页确实 push 了 → 但它落在覆盖层**下面** →
用户看到的是「点了菜单没反应」。

把层放进 AppShell 的 Stack 就没这个问题：路由管理器管不到它，
Stack 的 z 序是写死的。

**⚠️ 第二个坑：空判断不能放在 `ListenableBuilder` 外面**

`buildLayer()` 一开始写成：

```dart
Widget buildLayer() {
  if (_sessions.isEmpty) return const SizedBox.shrink();   // ← 错
  return ListenableBuilder(listenable: this, builder: ...);
}
```

`AppShell` 并不监听 `MiniappHost`，所以「打开第一个小程序」时
`_sessions` 从空变非空，但 AppShell 没有理由重建，`buildLayer()`
也就不会重跑 —— 这一层**永远停在那块 `SizedBox.shrink()`**。

症状：点「进入测试小程序」，页面什么都没出现（像白屏 / 闪退）。

正确写法是把空判断放进 builder：

```dart
Widget buildLayer() {
  return ListenableBuilder(
    listenable: this,
    builder: (context, child) => _sessions.isEmpty
        ? const SizedBox.shrink()
        : _buildLayer(),
  );
}
```

`test/miniapp_layer_test.dart` 钉住了这一点：打开会话后，
`MiniappSessionView` 必须真的出现在 widget 树里。

**代价**：系统返回键到不了这个层（它不是路由），所以必须由根路由的
`PopScope` 接管（见 `app.dart` 的 `AppShell`）。

### 返回键语义

| 情况 | 行为 |
| --- | --- |
| 小程序内有 WebView 历史 | 回退历史 |
| 退无可退 | **转后台运行**（不销毁），弹提示 |
| 前台无小程序、不在主页 Tab | 先回主页 |
| 已经在主页 | 交给系统退出 App |

用 `canPop: false` 显式接手，是因为「转后台」这个语义**没有办法用 Navigator 表达**
（它不是 pop，页面还在）。

### IndexedStack 保活的原理

`IndexedStack` 会**布局**所有子节点但只**绘制**选中的那个。所以：

- 后台会话的 WebView 尺寸不会塌成 0（不会触发页面 resize 重排）；
- 又不会被画到屏幕上、也收不到点击。

切到后台时还会显式调 `InAppWebViewController.resumeTimers()` ——
不可见的 WebView 会被 Chromium 降频，这是 Android WebView 官方给的
「我在后台但别停我」开关。

**诚实边界**：这是**进程内**保活。Android 在内存紧张时仍可能回收整个进程，
那不是框架能保证的。不做前台 Service（会让用户看到常驻通知，
且与本框架「轻量」的定位冲突）。

### 会话生命周期

```dart
MiniappHost.instance.open(appId: ..., title: ..., url: ..., localAsset: ...)
```

- 同一个 `appId` 只会有一个会话：重复打开 = 把已有会话切到前台；
- `open()` 里会先 `_popToShell()` 再 `_attachOverlay()`，保证层序正确；
- 会话登记到 `ApplicationRegistry`（应用管理的清单来源）。

`MiniappSession` 上挂了三个回调，由视图层注入：

| 回调 | 谁注入 | 用途 |
| --- | --- | --- |
| `onSystemBack` | `miniapp_page.dart` | 回退 WebView 历史 |
| `onResumeTimers` | 同上 | 切后台时让 JS 定时器继续跑 |
| `onReload` | 同上 | 重新加载页面 |

会话被 `dispose` 时这三个回调会被置空（避免操作已销毁的 WebView）。

### WebView 重建的坑（已规避）

`InAppWebView` 的 `initial*` 参数只在创建时生效。如果每次 `build`
都传一个新对象，插件可能判定配置变化而重建 WebView，导致小程序被重新加载。

规避方式（`miniapp_page.dart`）：

- `initialSettings` 做成 `static final`，保证 widget 恒等；
- WebView widget 只构建一次并缓存（`_webViewWidget`），主题变化只走 JS 热更新。

## 6. 权限模型（两层授权）

> **这一节在 0.3 重写过。读之前先忘掉 0.2 的模型。**

### 0.2 错在哪

0.2 把音量、亮度、屏幕方向、后台运行、文件都做成了「权限开关」。
Android 本来就不禁止应用调整音量与亮度 —— 把这些摆在权限管理器里，
只会让用户面对一堆「点了也没有实际意义」的开关，真正的风险项反而被淹没。

0.3 把这些能力**一律直接放行**（`bridge_api.dart` 里没有权限闸门，
这一点有测试守着），权限只管三件事 —— 网页真正能拿到的受控资源。

### 三项受控资源

| 权限 | 风险 | 对应 Web API | Android 运行时权限 |
| --- | --- | --- | --- |
| `camera` | 敏感 | `getUserMedia({video})` | `CAMERA` |
| `microphone` | 敏感 | `getUserMedia({audio})` | `RECORD_AUDIO` |
| `geolocationFine` | 敏感 | `navigator.geolocation`（精确） | `ACCESS_FINE_LOCATION` |
| `geolocationCoarse` | 敏感 | `navigator.geolocation`（大致） | `ACCESS_COARSE_LOCATION` |
| `clipboard` | 敏感 | `navigator.clipboard.read()` | 不需要 |
| `notifications` | 常规 | `Notification.requestPermission()` | `POST_NOTIFICATIONS` |
| `sdcard` | 高风险 | File System Access API | 不需要（系统选择器逐次确认） |

### `sdcard`：为什么不是「管理所有文件」

0.1.5 把这一项从 `allFiles` 改成了 `sdcard`（旧 id 仍作为别名识别，
用户以前点过的决定继续生效）。原因是一条很容易被忽略的边界：

| 位置 | 需要授权吗 |
| --- | --- |
| 小程序自己的两个沙箱目录（`FileScope.files` / `private`） | **不需要** —— 那是它自己的数据 |
| 手机存储的其它位置（Download、Pictures、DCIM …） | 需要，也就是 `sdcard` |

区别在于「谁的东西」：沙箱目录归小程序自己，宿主在桥接层直接放行；
沙箱之外的 sdcard 是用户和别的应用的数据，必须经用户点头。

授权之后也不是"拿到整块存储"：实际动作是 Chromium 弹出系统文件选择器
（SAF），用户选中的文件/目录才真正对页面可见。宿主**不申请**
`MANAGE_EXTERNAL_STORAGE` —— 那种「管理所有文件」的授权正是这次要去掉的东西。

### 定位：为什么拆成两档，且不在 onPermissionRequest 里

**拆两档的原因**：Android 12+ 把定位拆成了 FINE / COARSE，系统授权框也让
用户二选一（「精确」/「大致」）。宿主如果只做一个「定位」开关，
就等于替用户决定了精度。

拆开后：用户只同意「大致」时我们**只申请 COARSE**，Android 自己会把
坐标模糊到街区级；同意「精确」才申请 FINE。

⚠ 注意 Android 的规则：**申请 FINE 时会同时要求 COARSE**，
所以只声明 COARSE 才是「我只要大致位置」。

**为什么不在 `onPermissionRequest` 里**：Android WebView 根本不会为定位
回调那个方法 —— 定位走的是 `WebChromeClient` 上另一个回调
`onGeolocationPermissionsShowPrompt`。所以定位的拦截在
`miniapp_page.dart` 的那个回调里，映射函数是
`WebPermissionAsk.forGeolocation()`。

把 `GEOLOCATION` 写进 `from()` 的映射表只会让人以为它在那儿被拦了 ——
有一条测试专门钉住「定位在 `from()` 里是 unmanaged」。

`retain` 参数一律传 `false`：`true` 会让 WebView 记住这个 origin 的决定，
后续同源请求不再回调我们 —— 那样用户在权限管理里改成「拒绝」就不生效了。

真相来源：`lib/data/models/miniapp_permission.dart` 的 `MiniappPermission` 枚举。
每一项自带 `runtimePermissions` 字段（这就是「第二层」的声明）。

### 为什么是拦截而不是自己实现

小程序就是 WebView 里的网页，它要拿摄像头只会走 `getUserMedia()`。
这条路径由 Chromium 自己实现（采集、编码、生命周期、与 `<video>` 的对接），
宿主**一行原生采集代码都不用写**。

宿主该做的只有一件事：在 Chromium 弹出它自己的授权框之前把它拦住，
换成我们的模型。拦截点是 `InAppWebView` 的 `onPermissionRequest`
（对应 Android 的 `WebChromeClient.onPermissionRequest`），
实现在 `lib/bridge/web_permission.dart`。

### 两层授权，缺一不可

```
网页调 getUserMedia()
    ↓
Chromium 发起 onPermissionRequest（只告诉宿主「想要摄像头」）
    ↓
【第一层】宿主弹自己的框 → 用户点允许（PermissionService 三态决定）
    ↓
【第二层】NativeBridge.requestRuntimePermissions([CAMERA])
    → MainActivity.requestPermissions → 系统授权框
    ↓
拿到系统权限后，才回 PermissionResponse(GRANT)
    ↓
Chromium 真正打开采集设备
```

**顺序至关重要**：WebView 的 `onPermissionRequest` **不会**替宿主申请系统权限，
而 Chromium 真正开设备时 Android 还会拦一道。如果先回 ALLOW 再去申请，
用户会看到「弹窗点了允许，摄像头却打不开且没有报错」——
这是最难查的一类故障。所以顺序写死在 `miniapp_page.dart` 的
`onPermissionRequest` 里，注释也写在那儿。

**清单必须声明** `CAMERA` / `RECORD_AUDIO`（`AndroidManifest.xml`）。
不声明的话申请会被系统立刻拒绝，症状同上。`MainActivity` 里还会用
`getPermissionInfo()` 过滤一遍：只申请清单里真有的权限。

### 三态决定

| 状态 | 什么时候 | 行为 |
| --- | --- | --- |
| `ask` | **默认**，没写过记录 | 下次请求时弹窗 |
| `granted` | 用户点过允许（且取消了「仅本次」） | 直接放行 |
| `denied` | 用户点过拒绝，或在权限管理里改成拒绝 | Chromium 收到 DENY |

持久化：`perm.decision.<appId>.<permissionId>` → `'granted'` / `'denied'`。
**没写过 = ask**（而不是写一个 `'ask'` 值）：少一个状态就少一处不一致。

### 「仅本次生效」默认勾选

弹窗里那个复选框**默认是勾上的**，此时用户的选择**不落盘**，下一次还会问。

理由：权限弹窗最容易被用户当成必须点掉的拦路虎，手一快就点了允许，
而这个决定会一直生效。默认不记住，就把「长期授权」变成一次
需要用户主动取消勾选的、有意识的选择。

实现上：`PermissionAnswer.remember == false` 时 `_askSingle()` 直接返回答案、
不调 `setDecision()`。

### 翻译与回包的三条规则

`web_permission.dart` 里有两个纯函数，值得单独理解：

**规则 1：一次请求可能要问几项**

`getUserMedia({video:true, audio:true})` 是一个复合资源 `CAMERA_AND_MICROPHONE`，
翻译成 `camera + microphone` 两项，逐项问用户（他可能只想给麦克风）。

回包时**只有两项都同意才放行这个复合资源**，否则整体 DENY：

```dart
if (needs.every(granted.contains)) allowed.add(resource);
```

混进去一半等于偷偷放行。

**规则 2：不认识的资源要放行**

`AUTOPLAY`、`GEOLOCATION` 这些我们不管理的资源，直接交给 Chromium 的默认行为。
不能因为不认识就把页面功能掐掉 —— `isUnmanaged` 就是为这个存在的。

**规则 3：fail closed**

拿不到可以弹窗的地方（没有可用的 Navigator）时按**拒绝**处理，
并且**不写决定** —— 否则一次意外就把用户永久钉在「拒绝」上；
而 fail open 更不可接受。

### 两处询问入口

同一个三态决定有**两个触发点**，改动询问逻辑时两边都要看：

| 入口 | 什么时候 | 形态 |
| --- | --- | --- |
| `requestDeclared` | 用户在详情页点「打开」时（`app_detail_page.dart:274`） | 把 `apps.permissions` 里**还没问过**的声明项合成**一个**弹窗 |
| `ensureAll` | 网页运行时调 `getUserMedia()` | 逐项问（`getUserMedia({video,audio})` 会连弹两个） |

两条路径共用 `PermissionService` 的三态决定，所以**问过的不会再问** ——
用户在打开时答过「允许并记住」，运行时就不会再弹。

`requestDeclared` 必须在 `MiniappHost.open()` **之前**调用：
`open()` 会把路由收回外壳层，之后再弹窗就会隔着小程序覆盖层，交互很怪。
这一点在 `_openMiniapp()` 里写死了顺序。

### 并发与串行化

`PermissionPromptService` 里有两层保护：

- `_inFlight`：同一个 `appId|permissionId` 的并发请求共用一次弹窗；
- `_queue`：所有弹窗串行，同一时刻只有一个对话框（模态框叠起来
  没人知道在答哪一个）。

### 申请记录

`perm.usage.<appId>.<permissionId>` → `{c:成功次数, d:被拒绝次数, f:首次时间, l:最近时间}`。

于是权限管理第一屏能回答「哪些应用真的在用摄像头」，而不是只列一堆开关。
成功的与被拒绝的都记。

## 7. 应用清单与数据面

### ApplicationRegistry 是唯一真相来源

0.2 里「本机有哪些小程序」散在三处：权限服务的 `known_apps` 注册表、
`SharedPreferences` 里出现过的 appId、以及两个 `appfiles` 目录名。
每一处都只能看到一部分真相，于是「权限管理里列着某个小程序、应用管理里却没有」
这种不一致迟早会发生。

0.3 收成一份：`lib/data/services/application_registry.dart`。

```dart
class RegisteredApp {
  final String id;
  final String name;
  final String? icon;
  final String? url;
  final String? category;
  final DateTime? firstSeenAt;
  final DateTime? lastOpenedAt;
}
```

持久化在 `apps.registry`；旧数据（`perm.known_apps`）在第一次读取时自动迁移。

**为什么仍然要持久化而不是每次扫目录**：小程序是远程 HTML，没有「安装」概念，
目录里也不会留下 tarball。**打开过**就是唯一可靠的「这个 appId 存在过」的证据。
目录扫描仍被当作**补充来源**（用户手工往 appfiles 里放东西也算数），
只是它补进来的条目只有 id，没有名字和图标。

### 联动是单向的

| 页面 | 数据来源 |
| --- | --- |
| 应用管理 | `ApplicationRegistry.instance.all` |
| 权限管理 | `PermissionService.scan()`，第一来源是 registry |
| 存储页 | `MiniappStorageService.scanAll()` + registry 补名字 |

**只有一个方向能删**：`ApplicationRegistry.remove(appId)` 会同时清掉
权限决定与申请记录（`_clearPermissionRecords`）。反过来不行 ——
权限管理里没有「移除应用」这个动作，它只能改决定。

这样不会出现「应用没了、权限还留着」，也不会出现「权限管理删了应用、
应用管理还在」。

### 数据面：双作用域文件沙箱

每个小程序**两个**根目录：

| scope | 路径 | 可见性 |
| --- | --- | --- |
| `files`（默认） | `Android/data/<包名>/files/appfiles/<appId>/` | 用户能拷走 |
| `private` | `data/data/<包名>/files/appfiles/<appId>/` | 只有宿主读得到，卸载即消失 |

**为什么做成可选的**：两个目录的可见性完全不同，该用哪个由小程序的数据语义决定，
框架不替它猜。默认仍是 `files`，所以既有小程序行为不变。

**键值存储不分作用域**：`miniapp.storage.<appId>.<key>` 本来就在应用私有目录里。

### 路径安全的四道防线

`MiniappStorageService.normalizeRelativePath()`：

1. 只接受相对路径 —— `/etc/passwd`、`C:/...` 直接拒绝；
2. `..` / `../x` / `a/../../x` 一律拒绝（目录内的 `a/../b` 会被规范化成合法路径）；
3. 规范化之后，解析出绝对路径再 `isWithin` 校验一次（两道防线）；
4. 单次写入上限 8MB，路径长度上限 512 字符，递归统计有条目数上限。

**两个作用域共用同一套校验**，所以「换个 scope」不会削弱任何一条约束 ——
逃逸出哪一个都不行。

失败转成 `10001`（参数错误）而不是 `90001`（内部错误）：
小程序需要能区分「我参数写错了」和「框架炸了」。

### 占用统计与清理粒度

| 项 | 存储 | 统计方式 |
| --- | --- | --- |
| 键值 | `SharedPreferences` | 值的 UTF-8 字节数，精确到单键 |
| 文件 | 两个 `appfiles/<appId>/` | 递归统计文件数与总字节 |

清理从细到粗：单键 → 清空键值/清空文件目录 → 清除全部数据 → 清理全部。

**「清除数据」不重置权限授权**：授权是用户对该小程序的信任决定，
清数据是数据面的事。混在一起会让「清完数据还得重新授权」变得莫名其妙。
要重置授权去权限管理点「恢复默认」。

## 8. 模块与扩展包

### 两种包

| type | 能做什么 | 目录 |
| --- | --- | --- |
| `extension` | 往匹配的页面注入 CSS / JS | `<docs>/lemonlite/extensions/<id>/` |
| `module` | 注入脚本 **+** 通过 `manifest.bridge` 声明新 API | `<docs>/lemonlite/modules/<id>/` |

`<docs>` 是 `getApplicationDocumentsDirectory()`。

### manifest 格式

```json
{
  "type": "module",
  "id": "com.example.demo-module",
  "name": "示例模块",
  "version": "1.0.0",
  "description": "…",
  "author": "someone",
  "matches": ["*"],
  "runAt": "documentEnd",
  "css": ["inject.css"],
  "js": ["inject.js"],
  "bridge": [
    { "name": "ping", "action": "const", "params": { "value": { "pong": true } } },
    { "name": "fetchConfig", "action": "http.get",
      "params": { "url": "https://example.com/config.json" } }
  ]
}
```

两个容易写错的字段：

* `runAt` 是**驼峰**，取值只有 `documentStart` / `documentEnd`
  （解析器会 `toLowerCase()` 比对，所以 `document_end` 这类写法会静默落到默认值
  `documentEnd`，不报错 —— 但语义可能不是你要的）。
* `action: "const"` 返回的是 `params.value`，不是整个 `params`。
  写 `"params": { "pong": true }` 得到的是空对象。

现成的两个包可以直接对照：`docs/bundles/src/demo-extension/lemonlite.json`
与 `docs/bundles/src/demo-module/lemonlite.json`。

解析原则与市场数据一致：**宽松读取 + 结构性错误才抛**。
但比市场数据严格一点：`id` / `type` / `version` 缺失直接判为非法包 ——
它们决定落盘目录名与是否覆盖已有包，猜错会留下坏数据。

### 模块的 action 白名单

模块**不能带 Dart**。`manifest.bridge` 只能用宿主已实现的 action：

```
const / http.get / http.post / storage.{get,set,remove,clear,keys}
ui.toast / ui.setTitle / shell.openUrl
```

导入时会校验（`BundleBridgeMethod.supportedActions`），不支持的直接拒绝 ——
避免「装进去才发现不能用」。

另有 `reservedNames`：模块不能覆盖宿主内置方法名（`getSystemInfo`、`getTheme` 等）。

### 注入顺序与隔离

```
主题数据 → JS SDK → 包清单（window.__LEMONLITE_BUNDLES__）→ 扩展/模块脚本
```

**扩展 JS 一律包进 IIFE**：扩展作者不该能把变量漏到页面全局上互相污染。

**扩展的 JS/CSS 用「建 `<script>`/`<style>` 再插入」的方式执行**，
而不是拼进主脚本：这样扩展代码自己抛错时，宿主框架仍然正常，
错误落到 `window.onerror` 而不是崩掉注入。

**模块声明的桥接方法生成 `lemonlite.<name>()` 包装**，
脚本仍走同一条 `callHandler` 通道，不额外开后门。

### 解压的安全上限

| 限制 | 值 |
| --- | --- |
| 条目数 | 200 |
| 单文件 | 2 MB |
| 解压后总计 | 8 MB |

另外拒绝 `..` 与绝对路径；`id` 会当目录名用，非法 id 在解析阶段就被拒。

### 启停的语义

真相来源是**扫描目录**，不是 SharedPreferences。
prefs 只存停用名单（`bundles.disabled_ids`）。

**启停只影响下次打开**小程序；已经打开的页面需要重新进入。
这一条在 UI 上也写了（避免用户以为立刻生效）。

## 10. 服务端（唯一市场后端）

客户端**只支持服务端**一种后端（0.5 起）。

### 为什么删掉了静态 index.json

0.4 时客户端同时支持两条路：静态 `index.json`（全量）与服务端（分页）。
那意味着：

* 两套分页语义（全量 vs 游标）
* 两套搜索实现（本地 filter vs 服务端 query）
* 两套错误处理，以及一堆 `_useFeed ? ... : ...` 的分支

维护成本远大于它带来的便利，而用户实际只会选一种。0.5 删干净了：

| 删掉的东西 | 原因 |
| --- | --- |
| `MarketRepository.fetchIndex()` | 唯一数据源现在是 `/api/market/feed` |
| `MarketRepository.ensureApiAvailable()` | 不需要再「探测是哪种后端」 |
| `MarketIndex` 模型 | 它只是 index.json 的顶层结构；现在用 `MarketFeedPage` |
| `HomeController._useFeed` 分支 | 只有一条路，分支没有意义 |
| `kMarketIndexFile` 常量 | 没有 index.json 这个概念了 |
| 开发者页的 index.json 行 | 同上 |
| `docs/index.json` | `docs/` 现在只托管示例小程序页面 |

**旧地址的表现**：用户的服务器地址如果还指向一个静态站点，
`/api/market/feed` 会 404，主页显示通用的加载失败。
不做「检测到静态站点就特殊提示」——那需要为一条已废弃的路径保留探测逻辑，
而这正是这次要删掉的东西。

### 数据从哪来

服务端是 Node.js + MySQL，代码在 `server/`，部署说明见 `server/README.md`。

```
GET /api/market/feed     主页推荐（游标分页）
GET /api/market/search   搜索（关键词 + 标签）
GET /api/market/app/:id  单个应用
GET /api/market/tags     全量标签
```

### 两个 API 的分页方式不同（刻意的）

**`/api/market/feed` 用游标**：

```
GET /api/market/feed?limit=20&cursor=<base64url>
→ { data: { apps, categories }, meta: { nextCursor, hasMore } }
```

游标是 `<sort_weight>|<updated_at>|<id>` 的 base64url（去 padding）。
用游标而不是 offset 的原因：

> 应用列表会随时更新。offset 分页时，如果第 1 页之后有新应用插到最前面，
> 第 2 页会把第 1 页的最后几条**重复**返回一次 —— 用户看到重复卡片。

排序键 `sort_weight DESC, updated_at DESC, id ASC` 里的 `id` 不是装饰：
同一批导入的应用 `updated_at` 完全相同，没有第三个字段的话 MySQL
每次返回的顺序可能不一样，游标就会漏条目。

**`/api/market/search` 用 offset**：

搜索结果量级小（几十到几百条），offset 没有性能问题；
而用户会想「跳到第 2 页」，游标做不到。这是对上面规则的刻意破例。

### 搜索返回的标签是「命中结果里的」

```json
{ "data": { "apps": [...], "tags": [{ "name": "效率", "slug": "productivity", "count": 3 }], "total": 12 } }
```

不是全量标签表 —— 否则 chip 上会出现「点了没结果」的标签。

标签用独立表（`tags` + `app_tags`）而不是 `apps.tags` 这个 JSON 数组：
需要按标签反查应用（JOIN 走索引，`JSON_CONTAINS` 不走），
也需要统计每个标签下的应用数。

### 账号：登录态落库，不是纯 JWT

```
纯 JWT：签出去就收不回 —— 用户点「退出所有设备」、
        或者手机丢了要踢掉某台，服务端只能干等到过期。
落库后：每次鉴权查一次 login_sessions（主键查询），撤销是一条 UPDATE。
```

token 是 `lmn_` + 32 字节随机数的 base64url（43 字符）。
**数据库存的是 SHA-256**，不存明文：库被拖走时明文 token 等于把所有人的
登录态送出去；哈希之后攻击者还得反推 32 字节随机串。

`last_seen_at` 的写入做了节流（每 token 60 秒最多一次）：
否则高频接口上每个请求都会产生一次 UPDATE，写放大很明显。

### 两张表的字段

| `users` | 说明 |
| --- | --- |
| `id` | 自增，同时是 `userdata/<id>/` 的目录名 |
| `username` | 唯一，可改。排序规则大小写不敏感 |
| `email` | 唯一，可改 |
| `password_hash` | bcrypt。**任何接口都不返回它** |
| `avatar_ver` | 头像版本戳（上传时间），客户端拿它做缓存键 |
| `created_at` / `created_ip` | 注册时间 / 注册 IP |

| `login_sessions` | 说明 |
| --- | --- |
| `token_hash` | 主键（SHA-256） |
| `user_id` | 外键 → users.id |
| `created_at` / `last_seen_at` | 登录时间 / 最近活跃 |
| `expires_at` | 过期时间，与客户端拿到的有效期一致 |
| `login_ip` / `device` | 登录 IP、设备描述（客户端上报） |
| `revoked` | 撤销标记（不物理删行，保留审计线索） |

**登录失败不区分「用户不存在」与「密码错」**，并且用户不存在时也跑一次
bcrypt（`burnPasswordTime`）—— 否则响应时间本身就是用户名枚举信道。

### 用户文件：`userdata/<id>/`

```
userdata/7/data.json     用户私有 JSON（客户端任意结构，服务端不解释）
userdata/7/avatar.png    头像（固定文件名，覆盖式更新）
```

**不入库**：这两个都是「一整块不透明数据」，塞进 MySQL 只会让每次读写
变成「读一行 → 解析 JSON → 改 → 再序列化」。磁盘上是原子文件替换
（写 `.tmp` 再 `rename`），用户要备份直接拷目录。

**`userdata/` 不挂 `express.static`**：目录里有 `data.json`，
静态挂载等于把它们全部公开可下载（id 是自增的，谁都能挨个试）。
头像走 `/api/upload/avatar/:id`（只回图片 + ETag），
`data.json` 走需要登录的 `/api/user/data`。

### 头像：裁剪必须在客户端

服务端只做三件事：**是不是图**（看文件头魔数，不信 Content-Type）、
**多大**、**存下来**。

裁剪是交互（缩放、拖动、实时预览），只能客户端做。
实现见 `lib/pages/account/avatar_cropper.dart`，纯 Flutter 没有原生依赖 ——
导出时的做法是「用 `PictureRecorder` 按当前变换重画同一块区域」，
所以**看到什么就得到什么**，不需要反推变换矩阵。

导出固定 512×512：头像在客户端最大显示 72dp（3x 屏 = 216px），
512 留了余量，同时把上传体积压在几十 KB。

### 客户端账号的「未登录是合法状态」

`AccountService` 里没有「未登录就跳登录页」的逻辑，只有 `isLoggedIn`
这一个查询位。市场浏览、小程序运行、权限管理、存储管理全都不需要登录。

`init()` 只从本地读 token，**不等网络**；`withProfile: true` 时才后台静默校验。
校验失败分两种：

* `401`（token 被撤销 / 过期 / 改了密码）→ 清本地状态；
* 网络错误 → **保留**登录态（否则「飞机上打开 App」会变成「突然未登录」）。

## 11. 小程序包：下载、校验、升级

> 0.6 的核心变化：小程序**不再是远程网页**，而是下载到本机的 zip 包。

### 为什么要包化

| 远程网页（0.5 及之前） | 本地包（0.6） |
| --- | --- |
| 断网打不开 | 断网可用 |
| 每次打开都重新拉页面 | 从磁盘加载 |
| 没有「装的是哪一版」 | 版本明确，可回滚 |
| 服务端改了立刻生效（也可能是坏事） | 用户决定何时升级 |

### 数据流

```
服务端 /api/market/feed
    → { packageUrl, version, packageSha256, packageEntry, packageBytes }
        ↓  比对 MiniappPackageService.installed(appId)
    版本一致 → 直接 file:// 打开
    版本不同 → 下载 → 校验 sha256 → 解压 → 写 .complete → 切 current
        ↓
    WebView initialFile: file://.../miniapps/<appId>/<version>/index.html
```

### 目录布局与完成标记

```
<应用私有目录>/miniapps/<appId>/
├── current                  ← {"version":"1.1.0","entry":"index.html"}
├── 1.0.0/                   ← 旧版本（升级后由 pruneOldVersions 清掉）
└── 1.1.0/
    ├── .complete            ← 解压成功的唯一凭据
    └── index.html
```

**为什么需要 `.complete` 标记**：解压到一半被系统杀掉，目录会存在但不完整。
如果「目录存在 = 装好了」，下次打开就是白屏/404，而用户完全不知道发生了什么。
写标记是解压的最后一步；没有标记的目录一律当作损坏，`installed()` 返回 null
（于是会被重下）。

**写入顺序也很重要**：先写 `.complete`，再更新 `current`。
反过来的话，两步之间被杀会让 `current` 指向一个没标记的目录 ——
用户看到的是「白下了一次」。

### SHA-256 校验是必须的

```dart
final String actual = crypto.sha256.convert(await tmp.readAsBytes()).toString();
if (actual != expected) throw PackageException('checksum_mismatch', ...);
```

没有这一步，一个被劫持的网络就能塞进任意 HTML —— 而那个 HTML
能调**所有** JSBridge 能力（包括文件沙箱）。这是整个包流程里
唯一不可省的检查。

### 解压的路径安全

从网络来的 zip 是**不可信输入**。三道判断（顺序不能省）：

```dart
// 1. 绝对路径与盘符
if (raw.startsWith('/') || RegExp(r'^[A-Za-z]:').hasMatch(raw)) reject();

// 2. 目录穿越
if (normalized == '..' || normalized.startsWith('../')) reject();

// 3. 解析后的绝对路径仍须在目标目录内（兜底）
if (!p.isWithin(rootPath, outPath)) reject();
```

反斜杠要先归一成 `/`（Windows 打的 zip 会用 `..\..\x`）。
体积与条目数也有上限（80MB / 2000 个）—— 防 zip 炸弹。

`test/package_test.dart` 里用「等价逻辑」把这三道判断单独测了，
因为它们是纯字符串判断，不依赖真实文件系统。

### 升级检查

客户端在**主页**（不是启动时）调 `POST /api/market/updates`，
传已装列表 `[{id, version}]`，服务端返回版本不一致的那些。

**为什么不比较版本大小**：版本号没有强制语义（有人用 `1.0.1`，
有人用 `2026.10`），猜「哪个更大」会出错。**不一致就更新**是唯一
不会误判的规则。

**为什么做成 banner 而不是静默升级**：包可能几十 MB，
在移动网络下静默下载是**用户的钱**。升级必须是显式选择。

### 为什么不用「打开时顺便检查」

打开小程序时用户想的是「快打开」，不是「等它下载 30MB」。
所以：

* 详情页显示「已安装 v1.0.0 / 有新版本」+ 一个更新按钮；
* 主页显示「N 个小程序可更新」+ 全部更新；
* 点「打开」时如果版本不一致，才走下载（带进度对话框）。

### 服务端侧

`apps` 表的包字段：`package_url` / `package_entry` / `package_sha256` /
`package_bytes` / `version`。上传接口在一个事务里写这五件事 ——
否则会出现「版本号变了但包没变」，客户端会反复提示升级却升不上去。

包文件放 `packages/<appId>/<version>.zip`（保留历史版本，方便回滚与
多设备版本不一致时下载对应版本）。

演示数据的包由 `npm run seed:packages` 生成：它把 `docs/` 下的示例
打成 zip（自写的 `src/lib/zip.js`，120 行，不引 archiver/jszip），
算哈希并回填数据库。

## 12. 构建工具链与踩坑

### 环境要求

| 组件 | 版本 | 说明 |
| --- | --- | --- |
| Flutter | 3.47.7 | 与 CI 保持一致 |
| Dart | 3.13.5 | 随 Flutter |
| JDK | **17** | Gradle/AGP 不支持 JDK 21+ |

### 踩过的坑（按坑的严重程度排）

**1. `flutter_inappwebview` 必须锁 6.2.0-beta.3**

稳定版 6.1.5 依赖 `_android 1.1.3`，它的 `build.gradle` 用了
`getDefaultProguardFile('proguard-android.txt')`；而 Flutter 3.47 模板默认的
AGP 9.1.0 已经不再支持该文件，构建直接失败。
6.2.0-beta.3（`_android 1.2.0-beta.3`）改成了 `proguard-android-optimize.txt`。
等 6.2.0 正式版发布再换 `^6.2.0`。

**2. `file_picker` 不能乱升**

11.x 及更早在 AGP 9 下「故意不应用 Kotlin 插件」，依赖宿主开启 built-in Kotlin；
而 `flutter create` 默认写入 `android.builtInKotlin=false`，结果 Kotlin 源码不编译，
生成注册类找不到 `FilePickerPlugin`。12.x 换成了 `android_file_picker`，会自己读这个开关。
13.x 也修好了，但它要求 `win32 ^6.3.0`，会和 `package_info_plus` /
`device_info_plus` 抢版本 —— 所以锁 **12.3.0**。

**3. 插件注册只能走 `super.configureFlutterEngine()`**

`FlutterActivity.configureFlutterEngine()` 的实现就是调用
`GeneratedPluginRegister.registerGeneratedPlugins()`。
自己再调一次 `GeneratedPluginRegistrant.registerWith()` 等于把所有插件注册两遍 ——
`in_appwebview` 的 platform view factory 重复注册会直接抛异常。

**4. `flutter analyze` 在含中文的工程路径上会崩**

现象：`analysis server exited with code 255`，
`FormatException: Unexpected end of input (at character N)`。
原因：LSP 报文头里的长度按**字符**算，但 Dart 按**字节**读，中文路径让两者不一致。

绕法：`dart analyze`（直接调 Dart SDK，不走 flutter 的 LSP 封装）能正常工作。
CI 里路径是 ASCII，不受影响。

**5. 只读根文件系统**

如果宿主机根分区只读（容器 / 沙箱环境），Flutter 和 Gradle 都会失败：

- `flutter` 要往 `bin/cache/` 写 `engine.stamp`；
- Gradle 要往 `~/.android` 写 debug keystore；
- Gradle 的 `caches/*/transforms` 要求**同分区原子 rename**，
  overlayfs 做不到（报 `Could not move temporary workspace`）。

本仓库的 `.localbuild/run.sh` 是一个绕行方案（用户命名空间 + overlayfs +
真实 Gradle 缓存副本），细节见 `.localbuild/README.md`。
**正常机器上不需要它** —— 直接 `source ~/.lemonlite-toolchain/env.sh` 就行。

**6. `analyzer` 的 `deprecated_member_use` 被忽略**

`analysis_options.yaml` 里把弃用提示降级为忽略。原因：Flutter 近几个版本在批量
给 `ThemeData` 的组件主题参数改名（`CardTheme` → `CardThemeData` 等），
本工程刻意只用跨版本稳定的字段，不需要被这些提示淹没。

**7. `unawaited_return_in_try_block`**

`try { return someFuture(); }` 里 async 抛出的异常**不会被 catch 到**。
0.2 在文件 API 里踩过一次（33 处 `return` 全部补了 `await` 才真的成立），
差点写出一个静默失效的错误映射。

## 14. 已知边界与未验证项

### 设计上不做

| 不做 | 原因 |
| --- | --- |
| 原生渲染小程序页面 | 只做 WebView 承载；原生渲染是另一套完全不同的架构 |

### 已知的实现不完美处

**1. `PermissionPromptService.ensureAll` 是逐项问的**

`getUserMedia({video:true, audio:true})` 会连续弹两个框。
`requestDeclared`（打开小程序时的批量确认）是合成一个的，
但网页运行时的请求走 `ensureAll`，逐个问。

这是刻意的取舍：用户可能只想给麦克风，合成一个「允许/拒绝」会强迫他全给或全不给。
代价是连续两个弹窗。如果实测体验不好，可以改成一次弹窗里两个条目
（`permission_prompt.dart` 里已有批量弹窗的实现可复用）。

**2. `MiniappPermission.retiredIds` 是硬编码的**

0.2 的 10 个旧权限 id 写死在 `retiredIds` 集合里。
它们现在只用于「区分旧数据和拼错的 id」，不参与授权判定。
将来如果 0.4 再改权限模型，这个集合要跟着加。

**3. `application_registry` 的迁移只跑一次**

`_migrateLegacy()` 把 `perm.known_apps` 迁到 `apps.registry` 后就不再跑。
如果用户在迁移之后又用旧版本写入了 `perm.known_apps`（降级安装），
那部分数据不会被自动合并（但 `scan()` 仍会读它作为补充来源）。

**4. 测试没有覆盖 Widget 层**

`ApplicationsPage`、`PermissionControllerPage` 这些页面的状态机
（加载中 / 空 / 错误 / 正常）没有 widget 测试。它们靠人工点。

**5. `apps.permissions` 与运行时请求是两条路径**

打开前会按声明批量确认一次（`requestDeclared`），
运行时网页再请求时走 `ensureAll` 逐项问。
两条路径共用同一份三态决定，所以不会出现「打开时说允许、运行时又问一遍」
（问过的不会再问）—— 但**代码上确实是两处入口**，
改动权限询问逻辑时两边都要看。

### 下一阶段的候选

来自 `README.md` 第十五节，按价值排序：

1. **小程序包与安装**：服务端增加包地址与签名，持久化已安装列表，支持版本升级。
2. **更多浏览器受控资源**：地理位置、通知、剪贴板读写、相册 ——
   每一项都是「`MiniappPermission` 加枚举值 + `web_permission.dart` 加映射 +
   Manifest 加权限」三处，链路已经铺好。
3. **声明式权限的前置提示更细**：现在 `apps.permissions` 已经能在
   打开前批量确认一次，但它是「合并成一个弹窗」；下一步可以让每个资源
   单独说明用途（例如「需要麦克风是为了语音输入」）。
4. **域名白名单与配额**：`request` 只允许声明的域名，storage 与 appfiles 加配额。
5. **后台保活加固**：把「会被系统回收」变成可观测的（进程重启后恢复会话列表）。
6. **真机自动化**：现在是手工验证，缺一个能在 CI 里跑的
   Android 模拟器 + integration_test 方案。

## 15. 从 0.5 到 1.0 的演进

这一节记录 0.4 之后的重构。**大部分改动是「删」而不是「加」** ——
把不确定的东西砍掉，比不断叠加功能更能让项目活下来。

### 15.1 删掉了静态市场（0.5）

0.4 及之前有两套后端：静态 `index.json` 全量拉取，和 HTTP API 分段加载。
代码里到处是「先试 API，失败回落静态」的探测分支。

**问题**：两套分页语义、两套错误处理、两套搜索实现（一个在服务端、
一个在本地）。维护成本远大于它带来的便利，而且「回落」意味着
用户永远不知道自己在用哪个后端。

**做法**：彻底删除静态路径 —— 模型（`MarketIndex`）、常量
（`kMarketIndexFile`）、路由、文档、测试全部移除。
现在只有一个后端。

### 15.2 小程序改为「下载 zip 包」（0.5）

之前小程序是远程网页，用 WebView 直接打开 URL。改成**下载 zip → 解压 →
用 `file://` 打开本地文件**。

**为什么**：远程网页意味着每次打开都要联网、页面随时可能变、也没法做
完整性校验。包化之后可以校验 SHA-256，而且离线可用。

目录布局：

```
<support>/miniapps/<appId>/<version>/
├── index.html
└── ...（包内文件）
```

`current` 是一个 JSON 指针文件，指向当前生效的版本目录。
`.complete` 标记表示「这个版本解压完了」—— 解压中途崩溃不会留下半成品。

### 15.3 服务端包也改存外部 URL（0.6.5）

一开始服务端自己托管 zip（`packages/<appId>/<version>.zip`），
还为此写了分片上传（因为共享主机的 `upload_max_filesize` 只有 2M）。

**后来发现**：免费/共享主机的磁盘与带宽根本不适合托管几十 MB 的包，
而包是静态内容，天生适合 CDN。

**做法**：数据库里只存完整的外部 URL，客户端直接下载。
删掉了 `api/chunk.php`、`lib/upload.php`、`seed_packages.php`、
`packages/` 目录和相关配置。

服务端只剩三件事：存 URL、把相对路径补成绝对地址、版本检查。

> 关键约束：**服务端返回的必须是绝对 URL**。客户端拿到 `packageUrl`
> 就直接发请求，它没有「本站 base」概念（服务器地址由用户自己填，
> 可能带子路径）。返回相对路径会让客户端拼出错误地址，表现为 404。

### 15.4 权限从 3 个扩到 7 个（0.6）

原来是 `camera` / `microphone` / `file` 三个。改成浏览器可访问的
敏感设备权限：

| id | 说明 |
| --- | --- |
| `camera` | 摄像头 |
| `microphone` | 麦克风 |
| `geolocationFine` | 精确定位（GPS） |
| `geolocationCoarse` | 粗略定位（网络） |
| `clipboard` | 剪贴板读写 |
| `notifications` | 通知 |
| `allFiles`（0.1.5 起叫 `sdcard`） | 手机存储（沙箱之外）读取 |

**定位分两档是刻意的**：粗定位不需要 GPS 硬件、耗电低、隐私敏感度低，
很多场景（天气、附近）够用。让用户在「精确」和「粗略」之间选，
比只给一个「定位」更符合浏览器的实际模型。

`PermissionGroup` 把 7 个分成三组（媒体 / 位置 / 存储），
弹窗按组展示，避免一次问 7 个权限把人吓跑。

### 15.5 布局区分手机与平板（0.6）

断点是**最短边 dp ≥ 600**：

```dart
const double kTabletMinShortestSide = 600;

bool useWideLayout(BuildContext context) =>
    MediaQuery.sizeOf(context).shortestSide >= kTabletMinShortestSide;
```

手机：底部 `NavigationBar`。
平板：左侧 `NavigationRail` + 竖向分隔线。

用「最短边」而不是「宽度」：横屏的手机不应该被当成平板。

### 15.6 登录态用 token，但落库（0.6）

**不是纯 JWT**。token 是 32 字节随机数的十六进制（`lmn_` 前缀），
数据库里存它的 SHA-256。

**为什么落库**：纯 JWT 签出去就收不回。用户点「退出所有设备」、
或者手机丢了想踢掉某台设备，服务端只能干等到过期。
落库之后撤销是一条 UPDATE，立刻生效。

**为什么存哈希而不是明文**：库被拖走时，明文 token 等于把所有人的
登录态送出去；哈希之后攻击者还得反推 32 字节随机数。

两张表：

| 表 | 存什么 |
| --- | --- |
| `users` | id、用户名、邮箱、密码哈希、头像版本戳、状态、注册时间、注册 IP |
| `login_sessions` | token 哈希（主键）、用户 id、登录时间、最近活跃、过期、登录 IP、设备、撤销标记 |

### 15.7 开发者模式与运行日志（0.6）

**问题**：release 包里出问题时什么线索都没有。用户报「白屏」，
开发者只能猜。

**做法**：

1. `RunLog` 单例在内存里保留 2000 条日志（debug 和 release 都记）
2. `lemonLog()` / `lemonLogError()` 同时写 `debugPrint` 和缓冲区
3. 接上 `FlutterError.onError` 与 `PlatformDispatcher.instance.onError`
   —— **release 包里 build/布局阶段的异常原本会被静默吞掉**
4. 设置页「诊断 → 运行日志」可以筛选、复制、导出
5. 导出走**系统分享**（`share_plus`），能发微信/邮件/存到下载

> 第 5 点很关键：早期只是把文件写进应用私有目录
>（`/data/data/<pkg>/files/logs/`），然后把路径显示在界面上 ——
> 那个路径在未 root 的机器上用户根本进不去，等于没导出。

日志导出时会**脱敏**：`Bearer xxx`、`token=`、`password=`、`secret=`、
`api_key=`、`lmn_*`、三段式 JWT 都会被替换成 `***`。

### 15.9 共享主机的坑（实测记录）

这些都是**在真机上撞到并修掉**的，不是预防性设计：

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| `.env` 填了但一直连 `localhost` | 主机禁用了 `putenv`，`putenv()` 静默失败、`getenv()` 读不到 | 改用静态数组存解析结果 |

| `/api/` 返回落地页 | `$path` 归一化去掉了尾斜杠，`str_starts_with('/api', '/api/')` 为 false | 分流同时匹配 `/api` 与 `/api/...` |
| 500 但看不到原因 | 共享主机 `display_errors = Off` | 提供 `/install.php` 自检页 + `tools/check.php` |
| `.env` 解析失败 | `parse_ini_file` 遇到中文注释报语法错误 | 自己写 20 行解析器（只认 `KEY=VALUE` 与 `#` 注释） |

### 15.11 注册加邮箱验证码（0.1.1）

**为什么必须加**：邮箱地址不是秘密。没有验证就能用别人的邮箱注册，
一旦以后做了「邮箱找回密码」，这个账号就随时能被接管。
所以注册从「用户名 + 邮箱 + 密码」变成了「… + 服务端发到你邮箱的一次性验证码」。

服务端只加了一张表和两个动作：

```sql
email_codes(id, email, purpose, code_hash, ip, attempts, consumed, created_at, expires_at)
```

- **存哈希不存明文**：`sha256(email|purpose|code)`。6 位纯数字如果明文躺在库里，
  一次泄露就等于把所有「还没用掉的验证码」直接交出去。把 email 与 purpose
  一起拌进哈希，是为了让同一个码发给不同人时哈希不同。
- **时间由应用进程算好再写库**，不用 `NOW()`：DATETIME 不带时区，
  数据库与 Node 进程时区不一致时「过期没有」会判错，而这种错极难复现。
- **一次性 + 限次数**：核销成功立刻置 `consumed`；输错一次 `attempts+1`，
  超过上限（默认 5）直接作废 —— 否则六位数字慢慢试总能撞上。
- **限流三档**：同邮箱 60 秒冷却、单邮箱 10 封/小时、单 IP 30 封/小时。
  全部落在数据库里，多进程部署也成立。

**四条刻意保留「可能泄露信息」的取舍**（都写进了代码注释）：

1. 邮箱已注册时 `email-code` 直接回 409，而不是假装发送成功。
   遮着只会让用户对着一个永远收不到的信箱发呆 —— 而注册接口本来就会告诉他。
2. 验证码散列里带上 `purpose`，将来加「邮箱重置密码」时两套码互不干扰。
3. 发信失败时把刚插入的码**删掉**：否则用户会在冷却期里等一封永远不来的邮件。
4. 开发模式（`MAIL_DEV_ECHO_CODE`）把码放进响应的 `debugCode`，
   客户端据此自动填框 —— 这条在生产上是灾难，所以默认 `false`，
   并且单独在安全清单里挂了红牌。

**邮件通道抽象**（`src/lib/mailer.js` + `src/lib/smtp.js`）：

```
sendMail({to, subject, text, html})
   ├─ smtp      ← 自带极简 SMTP 客户端（node:net / node:tls，零依赖）
   ├─ resend    ← HTTP POST
   ├─ sendgrid  ← HTTP POST
   ├─ aliyun    ← RPC 签名（HMAC-SHA1）+ HTTP GET
   └─ console   ← 只打日志（开发）
```

为什么自己写 SMTP 客户端而不是装 nodemailer：我们需要的只是
`EHLO → STARTTLS → AUTH → MAIL/RCPT/DATA` 这一百来行对话。
正文一律 base64 传输 —— 中文邮件走 8bit 会被不少老 MTA 截断，
base64 是 ASCII 安全的，顺便绕开了「行首点号要转义」。
主题与发件人名按 RFC 2047 编码（`=?UTF-8?B?...?=`），
不编码的话中文主题在收件箱里就是一堆问号。

`npm test` 里用 `node:net` 起了一个假 SMTP 服务器，把整段对话的顺序、
中文主题编码、密码错误时的报错都断言了一遍 —— 这些恰恰是最难在真机上发现、
又最影响「用户到底能不能收到信」的部分。

### 15.12 一轮流畅度与动效改造（0.1.1）

「卡」和「没有动画」看起来是两件事，在这一版里其实是同一件事的两面：
**之前那唯一一处动画，正是卡顿的主要来源。**

**卡顿 · 找到的四个真凶**

1. **页面转场在每帧重新光栅化整屏**。旧实现是「整页 `Transform.scale` +
   逐帧变化的 `ClipRRect` 圆角 + `FadeTransition`」。视觉上像 M3E 的
   shape morph，代价是每次导航都要把整屏内容按新尺寸/新圆角重画一遍。
   现在只做**位移 + 透明度**（两者都是合成器能直接处理的层操作），
   圆角形变交回系统的容器转场。同样的观感，掉帧没了。
2. **图标按原图解码**。`Image.network` 不传 `cacheWidth` 时按原始像素解码，
   市场图标常见 512/1024 —— 一屏 5 张就是几十 MB 位图，
   滚动时的 GC 与纹理上传全压在这里。现在 `AppIcon` 按
   `size × devicePixelRatio` 解码，详情页截图同理。
3. **后台小程序的 JS 定时器一直在跑**。之前后台会话会显式调
   `resumeTimers()`「保活」。但用户在前面滑列表、后面有个小程序每 100ms
   跑一次 `setInterval`，掉帧根本查不出来。现在后台**挂起**（`pauseTimers`），
   回前台再恢复 —— 页面状态（DOM / 滚动位置 / 表单内容）一个都不丢。
   顺带也把「后台运行」从「后台耗电」里摘了出来。
4. **列表项没有重绘边界**。水波纹、按压动画会把整条列表一起重画。
   每张卡片包一层 `RepaintBoundary`，重画范围收敛到这一张卡片。

**动效 · 补了什么**

新增 `lib/theme/motion.dart`（只放「会跑起来的行为」，配置仍留在 `app_theme.dart`）：

| 组件 | 用在哪 | 做法 |
| --- | --- | --- |
| `StaggeredEntrance` | 主页列表、搜索结果、横幅 | 淡入 + 上移，按 index 错峰 45ms |
| `PressableScale` | 应用卡片 | 按下 0.975，由 InkWell 高亮回调驱动 |
| `StateTransition` | 加载 / 空 / 错误 | 交叉淡入，新内容从下浮入 3% |
| `_TabSwitcher` | 底部导航三 Tab | 切换时淡入（0.35→1）+ 上浮 6px |

加了一条贯穿全部动效的约定：**只动 `Transform` 与 `Opacity`**。
这两个属性不会触发 layout，也不会让 `RepaintBoundary` 失效。
另外所有动效都尊重系统「减弱动态效果」（`MediaQuery.maybeDisableAnimationsOf`），
开了就直接给终态。

还有一个容易忽略的细节：`StaggeredEntrance` 用的是
`TweenAnimationBuilder` 而不是 `AnimationController` —— 列表项会随滚动
反复创建销毁，每个都持有 controller 就要管 dispose，还要提防 Ticker 泄漏。
隐式动画由框架自己管生命周期，这类「只播一次」的入场应该用它。

### 15.13 登录二次验证与「永不过期」的 token（0.1.2）

**登录验证码**：注册的验证码只解决「邮箱是不是你的」，登录本身仍然一个密码说了算。
把同一套 `email_codes` 再用一次（`purpose='login'`），就得到可选的两步验证：

```
AUTH_LOGIN_CODE=off（默认） → 密码通过即登录
AUTH_LOGIN_CODE=on          → 密码通过 → 还要一个邮箱验证码
```

三个刻意的决定：

1. **发码接口必须先核对密码**（`POST /api/auth/login-code` 收账号 + 密码）。
   只凭账号发码的接口有两宗罪：能轰炸任意邮箱，能枚举账号是否存在。
   代价是用户在同一屏输两次密码 —— 客户端把「获取验证码」放在密码框右边，
   这个代价几乎看不见。
2. **先验密码、再验码**。验证码输错不该烧掉一个有效的码，更不该让不知道密码
   的人通过「码对不对」做试探。
3. **开关由服务端下发**（`GET /api/auth/config`）。客户端写死任何一边都会
   产生「客户端要码、服务端没开」这种永远登不进去的死局。所以注册页与登录页
   都在首帧后拉一次配置，再决定要不要渲染验证码输入框；即便拉取失败，
   服务端回一个 `code_required` 也能让界面当场把输入框展开。

**「客户端不卸载就一直有效」**：`TOKEN_TTL` 现在接受 `never`（新的默认值）。

- 落地方式是把 `expires_at` 写成一个远期时间（9999-12-31），列仍然是
  `NOT NULL`，所有 `expires_at > now` 的判断一个字都不用改。
- **「永不过期」不等于「不可收回」**：撤销仍然是一条 UPDATE 立刻生效
  （退出登录、踢掉某台设备、改密码踢掉其它设备、停用账号）。
- 同时给有限有效期补了**滑窗续期**：剩余不足一半时自动往后推一个完整周期。
  这样 `TOKEN_TTL=7d` 的语义是「丢掉的那份慢慢过期」，而不是
  「每周无差别踢所有人下线」。续期与 `last_seen_at` 共用同一个 60 秒节流，
  不会变成每个请求一次写库。

另外顺手修了一个时区隐患：`Date` 直接交给 mysql2 时会按**进程本地时区**
格式化，而读出来时代码又按 UTC 解析 —— 时区不是 UTC 的机器上会话会凭空
多出/少掉几小时。现在写入统一用显式 UTC 字符串（`toSqlTime`），两边同一个时钟。

### 15.14 管理面板与「配置即数据」（0.1.3）

邮件通道有十几个参数（主机/端口/授权码/API Key/限流阈值），让用户 ssh 上去
改 `.env` 再重启，等于把「配置」变成了「运维」。所以补了一块服务端直出的
`/admin`：概览、邮件通道、策略、用户列表。

**几个刻意的小决定**：

- **没有 `ADMIN_PASSWORD` 就不启用**。空口令的后台等于把「改发信通道」的
  权限公开（能改通道 = 能收走所有人的验证码）。默认关闭比默认 `admin/admin` 安全。
  （1.0 已改成数据库里的管理账号，见 15.15。）
- **改完立即生效，同时写回 `.env`**。只改内存的话重启就回到旧值，
  用户会以为「保存按钮没生效」；只改文件则要重启，用户会以为「保存了但没应用」。
  `.env` 的写入是逐行替换 `KEY=`，不重排、不删注释 —— 这个文件是给人看的。
- **密钥不回显**：GET 只返回 `passwordSet: true/false`，
  PUT 时留空表示「不修改」。否则面板本身就是一份凭据泄露面
  （浏览器缓存、截图、肩窥）。
- **不引任何 CDN**：内网服务器没有外网，一引 CDN 面板就白屏。
  页面是一段模板字符串，改文案不用重新构建。
- 登录态用 HMAC 签名的 cookie（含过期时间），不是明文口令；
  失败按 IP 限流（10 次 / 10 分钟）。

**「做全」之后补的三块**：

- **应用管理**：列表（含已下架）、新建、编辑、上架/下架、软删除，
  以及**上传 zip 包**。上传时会重算 SHA-256 与大小，并和版本号、入口、
  包地址**一次性**写库 —— 这五件事分开写就会出现「版本变了但包没变」，
  客户端会永远提示升级却升不上去。
- **用户管理**：封禁（同时撤销该用户全部会话，否则已登录的设备还揣着 token）、
  重置密码（同样踢下线）、单独踢下线。
- **分类/标签**：编辑器的下拉与多选数据来自 `/admin/api/meta`。
  标签只允许挂**已有**的，不顺手新建 —— 否则「标签」很快会变成一堆拼写变体。

顺手做的一次重构：包的路径拼装与 zip 魔数校验被抽到 `lib/package_store.js`，
作者上传接口（`/api/market/:appId/package`）与管理面板共用同一份。
原来两边各写一份 `packagePath()`，这种「安全校验复制粘贴」最危险的地方在于
两边会慢慢分叉，而分叉出来的那个洞通常没人发现。

**顺带的两处客户端行为修正**：

1. **详情页只剩一个「打开」**。安装是实现的细节，不是用户要理解的概念：
   没装过时按钮叫「下载并打开」，装过就叫「打开」——
   永远是同一个按钮、同一条路径（`ensureInstalled` → 下载 → `file://` 打开）。
2. **「移除应用」真的会删文件**。之前只从应用清单里注销，包还躺在磁盘上
   （`miniapps/<id>/`），用户以为清干净了。现在顺序是：先关后台会话
   （它的 WebView 还开着 `file://` 页面，文件删了一半再跑只会报资源丢失）→
   删包目录 →（可选）清数据 → 注销。

### 15.15 管理账号、多分类与分类标签管理（1.0）

0.1.3 的面板是「一个全服共用的 `ADMIN_PASSWORD`」。1.0 换成**数据库里的管理账号**：

- `admin_users` 表：用户名 + bcrypt 口令 + 组（目前只有 `admin`）+ 状态。
- **第一次访问时表是空的**，页面显示「创建管理员」，建完自动登录；
  之后同一个地址就是普通登录。没有默认口令，也就没有「默认口令忘了改」这件事。
- 之后新增管理员只能由已登录的 admin 在面板里加（需求明确：只加 admin 组）。
- 会话是 HMAC 签名 cookie，签名密钥里混入该账号的 `password_hash`：
  **改密码 = 这个账号所有旧 cookie 立刻失效**，不需要再维护一张 sessions 表。
- 首次建号用 MySQL 命名锁（`GET_LOCK`）串行化，两个请求同时到达也只会建一个。
- 最后一个可用管理员不能被停用/删除，自己也不能停用/删除自己 ——
  否则会出现「面板还在，但没人进得去」。
- 公网部署建议设 `ADMIN_SETUP_TOKEN`：建第一个号时必须填，
  把「部署完还没建号」那段空窗期也盖住。

**多分类**：`apps.category_id` 保留为主分类（客户端详情页只认一个字段），
新增 `app_categories(app_id, category_id)` 存完整归类。写入时两处一起改
（`replaceAppCategories`），读取以关联表为准、主分类兜底；
市场 feed 的分类筛选与分类计数都改成「主分类命中 **或** 关联表命中」。
升级上来的老库由 `lib/schema_guard.js` 在启动时幂等建表并回填
（`INSERT IGNORE ... SELECT`），所以 `git pull` 完直接重启也能用，
不依赖「记得先跑 npm run init」。

**分类/标签管理**：面板新增「分类标签」页（新建 / 改名 / 删除 / 分类排序）。
删除被应用使用的分类或标签**默认拒绝**：返回 409 + 还有几个应用在用，
确认后带 `?force=1` 才真的删 —— 一次误点不应该清掉整类应用。
分类 id 会出现在接口参数里，中文名转不出 ASCII 时生成 `cat_xxxxxxxx`。

顺带做的一次拆分：面板路由从单个 878 行的 `routes/admin.js` 拆成
`src/admin/{auth,apps,taxonomy,users,mail}.js` + `routes/admin.js` 只做装配。
理由是这次要往里塞「管理员账号」和「分类标签」两块，再堆下去
「哪些接口需要登录」会变成靠读到最后一行才知道的事；现在装配文件里
`adminRouter.use(requireAdmin)` 之前是公开接口、之后全是登录接口，一眼能看出来。

### 15.16 设置页收拢与客户端多分类（0.1.4）

设置页原来第二组就是「外观」，主题模式、动态取色、种子色三块全摊在一级页面，
把「账号」挤到了下面。0.1.4 的调整：

- **账号移到第一位**：设置页第一件事就是登录态；未登录时它本身就是「去登录」入口。
- 颜色那三项收进二级页面「个性化」
  （`lib/pages/settings/personalization_page.dart`），一级页面只留一行入口。
- 顺手删了两处过期/多余的文案：登录页的「这台服务器开启了两步验证」
  （验证码输入框出现本身就说明了这件事）、设置页底部「第一阶段只做 WebView 承载」
  （早就不是第一阶段了）。

**客户端多分类**：服务端 1.0 起一个应用可以挂多个分类。`AppItem` 增加
`categories: List<AppCategory>`，数据来自 DTO 的 `categories` 数组（始终是服务端给的）。
详情页头部 chip 仍只显示主分类（一行放不下多个），「分类」一行展示全部
（`工具 · 效率`）。`category` 字段保留为主分类 id：搜索与 feed 的 `category`
参数只认一个。

标签的来源本来就是服务端：卡片/详情用 DTO 里的 `tags`，搜索页的 chip 用
`GET /api/market/tags`。这次没有改数据来源，只确认了「面板新加标签 → 客户端刷新即出现」。

### 15.17 下载管理（0.1.5）

网页里的下载在 Android WebView 上是**什么都不会发生**的：WebView 没有内建下载器，
`<a download>`、`Content-Disposition: attachment` 都只会触发
`WebChromeClient.onDownloadStart`，宿主不接就静默失败。

接法（`lib/pages/miniapp/miniapp_page.dart`）：

```dart
onDownloadStarting: (controller, request) async {
  await _handleDownloadStart(request);   // → DownloadService.enqueue
  return DownloadStartResponse(
    handled: true,
    action: DownloadStartResponseAction.CANCEL,   // 别让 WebView 再走默认路径
  );
}
```

**落盘交给系统 DownloadManager**（`android/.../DownloadBridge.kt`），理由不是"省事"：

| 方案 | 问题 |
| --- | --- |
| Dart 直接写 `Download/` | Android 10+ 需要 MediaStore / SAF / `MANAGE_EXTERNAL_STORAGE` —— 最后一项正是本版本要避免的 |
| 写自己沙箱再导出 | 文件不在用户找得到的地方，与"下载"语义不符 |
| **系统 DownloadManager** | 落盘零权限、下载活过宿主进程、完成有系统通知 |

代价（有意接受）：宿主**读不了**那些文件（公共下载目录对外部应用不可读），
所以「打开」用 DownloadManager 签发的 `content://` Uri，「删除」用
`DownloadManager.remove()`（连文件一起删）。管理页展示的名字/大小/状态
全部来自自己的记录 + `query()`，不去 stat 公共目录。

其他实现要点：

* 权限：只有 **Android 9 及以下**需要 `WRITE_EXTERNAL_STORAGE`（清单里用
  `maxSdkVersion="28"` 收窄，新系统上连声明都没有），入队前申请一次。
* 文件名：`suggestedFilename > Content-Disposition（含 RFC 5987）> URL 最后一段 > 时间戳`，
  然后清洗（`/`、控制字符、前导点、超长截断）—— 文件名来自网页，是不可信输入。
* 目录：根固定是公共 `Download/`，可设一层相对子目录（`download.subdir`，默认空）。
  DownloadManager 只允许公共目录下的相对路径，这不是简化。
* 记录：`download.tasks`（上限 100 条），启动时按 id 回查真实进度；
  系统里已不存在的任务标为失败并说明原因，而不是悄悄消失。
* 页面：`lib/pages/download/download_page.dart`（设置 → 存储 → 下载管理）。
* 小程序也能主动存：`lemonlite.download.save(url, {fileName, mimeType})`。

### 15.18 权限 `allFiles` → `sdcard`（0.1.5）

原来的 `allFiles`（「管理所有文件」）名字把两件事混在一起了。这一版按
**"谁的数据"** 划线：

* 小程序自己的两个目录（`FileScope.files` / `private`）——**不需要授权**，
  桥接层直接放行（这一点从 0.3 起就是这样，没有变）；
* 沙箱之外的手机存储（Download、Pictures、DCIM …）——需要 `sdcard`，
  由系统文件选择器逐次确认。

实现细节：

* id 改成 `sdcard`，`label` 叫「读取手机存储」；
* `MiniappPermission.aliases` 把旧 id `allFiles` 映射到新枚举：市场数据里
  还在写 `allFiles` 的应用不算「未知权限」；
* `PermissionService.decisionOf()` 会按 `legacyIds` 回退读旧 key，
  升级前用户点过的「允许/拒绝」继续生效；写新决定时新旧 key 一起清，
  避免旧记录"复活"；
* `web_permission.dart` 的 `FILE_READ_WRITE` 映射到 `sdcard`。

### 15.19 插件体系与 wasm 插件化（0.1.5）

**先说清楚三者的区别**（这是这次最重要的一句话）：

| 类型 | 做什么 | 会不会改页面 |
| --- | --- | --- |
| 扩展 `extension` | 注入 CSS / JS | 会 |
| 模块 `module` | 注入 JS + 用宿主能力组合出新的 bridge 方法（mod 式） | 会 |
| **插件 `plugin`** | 给**宿主**增加一项能力，所有页面都能用；声明支持平台与能力 | **不会** |

插件 manifest（`lemonlite.json`，和扩展/模块共用一套格式，`type: "plugin"`）：

```json
{
  "type": "plugin",
  "id": "lemonlite.wasm",
  "name": "WebAssembly 运行时",
  "version": "1.0.0",
  "platforms": ["android", "ios", "macos", "windows", "linux", "web"],
  "capabilities": ["wasm"],
  "wasm": { "modules": [{ "name": "lemonlite", "file": "modules/lemonlite.wasm", "exports": ["add"] }] }
}
```

* 落盘/扫描/启停/原子写入全部复用 `BundleRepository`（`plugins/` 目录）；
* `PluginService` 只做两件事：判断「在这台设备上能不能用、是不是启用」；
  按能力读资源（目前只有 wasm 模块）；
* 平台不匹配的插件仍然出现在列表里（标「不支持」），不静默消失；
* 无 manifest 的 zip 包导入路径与扩展/模块完全一致（本地文件 → 预览 → 确认 → 落盘）。

**wasm 怎么"不内嵌"了**：`lib/core/builtin_wasm.dart` 已删除，宿主里不再有模块清单、
asset 路径与加载逻辑。模块字节来自插件包：`assets/plugins/lemonlite-wasm/`
是**随包附带的插件包**（不是宿主代码），装不装由用户在「设置 → 插件」决定 ——
装上之后和从 ZIP 导入的插件没有任何区别，也可以停用/卸载。
`lemonlite.wasm.*` 的 API 形状没变（老小程序不用改），只是背后改成
`PluginService → 插件目录`；没装插件时 `wasmRead` 返回 `10003` 并提示去装。

**为什么不做成"自动安装"**：插件给宿主加能力，用户应该知道自己装了它。
静默安装会让「为什么有个我没装过的东西在跑」变成一个无法回答的问题。

### 16.2 签名

正式签名用 RSA 2048 / SHA256withRSA，有效期 10000 天。

凭据在 `android/key.properties`（权限 600，已 gitignore），
密钥库在 `android/app/lemonlite-release.jks`。

`build.gradle.kts` 的逻辑：

```kotlin
val keystoreFile = rootProject.file("key.properties")
// 存在 → 正式签名；不存在 → 回落 debug（保证没配密钥的机器也能构建）
signingConfig = if (keystoreFile.exists()) {
    signingConfigs.getByName("release")
} else {
    signingConfigs.getByName("debug")
}
```

> ⚠️ Kotlin DSL 里 `java.util.Properties()` 会报 `Unresolved reference 'util'`
> —— `java` 被解析成 Gradle 的 `java {}` 扩展。必须在文件顶部
> `import java.util.Properties` 然后直接写 `Properties()`。
